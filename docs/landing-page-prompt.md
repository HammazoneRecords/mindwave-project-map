# Landing Page Build Prompt — MindWave Project Map

Create a launch-ready landing page for the open-source project **MindWave Project Map**.

The page should make the project feel like a precise instrument for turning a project into an inspectable field: what is true, what is being tested, what evidence exists, and what has been found. Do not make it sound like generic project-management software. Do not overstate the product. Keep the distinctions exact.

## Positioning

MindWave Project Map is an open-source way to represent a project as a structured map of facts, tests, evidence, and findings.

The core model is:

- **Map = facts** — the current structure, entities, relationships, states, and known conditions.
- **Journey = test / steer** — the active path of trying something, making a decision, or changing direction.
- **Trace = evidence** — the record that shows what happened, what supports a claim, or how a state was reached.
- **Findings = issues** — the problems, contradictions, gaps, risks, or unresolved conditions discovered along the way.

Do not collapse these categories into interchangeable labels. The Map is not the Journey. The Journey is not the Trace. Findings are not vague notes. Make the contrast visible throughout the page.

## Audience

Write for people who build, research, maintain, audit, or steer complex projects, including open-source maintainers, technical founders, product builders, researchers, designers, systems thinkers, and teams that need project state to remain inspectable as work changes.

Assume the reader is intelligent and busy. Explain the model plainly. Do not assume a specific industry, workflow, framework, or technical stack that has not been established.

## Page goals

1. Explain what MindWave Project Map is in the first screenful.
2. Show the Map / Journey / Trace / Findings model as the central organizing idea.
3. Make the project feel useful without claiming unbuilt features.
4. Establish that it is open source without inventing a license, repository URL, integrations, maturity level, user count, or roadmap.
5. Give visitors a clear next action: explore the project, view the source, or get involved. Use configurable placeholder URLs where needed.

## Required sections

### Hero

Use a direct headline that names the problem and the shape of the solution. Suggested direction: **Map the work. Test the path. Keep the evidence.**

Support it with a concise explanation and two CTAs:

- **View the project** — `[REPOSITORY_URL]`
- **Read the documentation** — `[DOCUMENTATION_URL]`

### The distinction

Create the strongest explanatory section on the page. Present four geometric, clearly differentiated blocks or a connected diagram:

- **Map / facts**
- **Journey / test + steer**
- **Trace / evidence**
- **Findings / issues**

Each block should have one short definition and one concrete, generic example. Keep examples illustrative, not claims about existing functionality.

### Why this shape

Explain the problem with mixing facts, activity, evidence, and issues into one undifferentiated project record. Facts tell you what the project is. Tests and steering tell you what is being attempted. Evidence tells you why a statement can be trusted. Findings tell you where the model or work does not hold yet.

### How to read a project

Show this sequence:

1. Establish the Map.
2. Choose or record a Journey.
3. Capture the Trace.
4. Surface the Findings.
5. Return to the Map with a more accurate view.

Frame this as a way to think and organize work, not as a claim that the software automates every step.

### Open-source invitation

State that the project is open source and invite readers to inspect, use, question, and contribute. Do not claim an active community, contribution volume, governance structure, license, or production readiness unless supplied as project data.

Suggested direction: **The structure is open to inspection. Start with the source, test the distinctions, and help sharpen what the map can hold.**

### Final CTA

Close with: **Start with the map. See what is known. Test what is next. Keep the trace. Name the findings.**

Buttons:

- **View on GitHub** — `[REPOSITORY_URL]`
- **Read the docs** — `[DOCUMENTATION_URL]`
- optional **Contribute** — `[CONTRIBUTING_URL]`

Do not add a newsletter, waitlist, pricing, demo booking, or sales flow.

## Visual direction

Design the interface as a geometric systems instrument, not a glossy SaaS dashboard.

- Use a strong grid, visible alignment, measured spacing, and clear hierarchy.
- Use diagrams, nodes, lines, axes, brackets, coordinates, and layered cards to suggest a living project map.
- Let the four core terms have distinct visual treatment while remaining part of one system.
- Favor dark ink, warm off-white or mineral surfaces, and a controlled accent palette.
- Let Jamaican/world-building influence appear through warmth, rhythm, color intelligence, and a sense of place—not decorative Patois, flags, clichés, or tourism imagery.
- Consider subtle references to horizon, route, terrain, signal, and constellation, but keep every metaphor tied to the operational model.
- Use readable typography. Avoid futuristic display fonts that reduce legibility.
- Motion, if used, should be quiet and functional: a line resolving into a node, a trace revealing its source, or a route changing direction.
- Make it responsive and accessible, with keyboard-visible focus states, semantic headings, descriptive link labels, and reduced-motion support.

## Copy guidance

Write in a direct, clean, systems-oriented voice.

- Use short paragraphs and load-bearing sentences.
- Name the object before explaining the atmosphere around it.
- Preserve contrast: **Map is facts. Journey is test and steer.**
- Use concrete verbs: map, test, steer, record, trace, inspect, surface, resolve.
- Allow world-building language only when it clarifies the system.
- Keep the tone confident but evidence-bound. Invite inspection; do not demand belief.
- Avoid generic corporate filler such as “seamless,” “revolutionary,” “empower,” “unlock,” “next-generation,” “holistic,” and “game-changing.”
- Do not insert Patois as decoration.
- Do not invent testimonials, metrics, integrations, technical architecture, commands, screenshots, workflow automations, or product capabilities.
- Do not flatten Findings into “insights,” Trace into “analytics,” Journey into “tasks,” or Map into a generic “workspace.”

## Implementation constraints

Build a polished, production-quality open-source project landing page. Keep content and links easy to replace. Use placeholder URLs for unknown destinations. Use semantic HTML, responsive CSS, accessible interactions, and no unnecessary dependencies. Avoid fabricated product UI beyond simple illustrative diagrams clearly marked as examples.

The final result should feel like a project with a real shape: direct, inspectable, geometric, warm, and ready to be tested in the world.
